## What's New

Bug-fix release: **three receive-path stability fixes** plus one diagnostic tool.
All were found by tracing reported symptoms — *on a UHF memory channel with a
repeater offset the RX audio opens and closes intermittently with spurious DTMF
digits on screen*, and *on one VFO of a band the S-meter moves and the squelch
opens but the speaker stays dead* — back through the tone, AGC and audio-path
state machines.

If you have been living with either, this release is for you. None of the three
defects exists upstream; all were introduced by this edition's spectrum, DTMF and
VFO work.

### 1. Spurious DTMF digits and choppy RX on repeater channels (RX-10)

- **Problem:** the DTMF decoder was **permanently armed** — the `D Live = off` menu
  setting could never actually take effect. Because the DTMF decoder is a tone
  detector sharing the CTCSS/tail filter bank, ordinary voice and noise energy on a
  UHF repeater carrier could raise false "code found" interrupts. Those were latched
  as real digits (hence the phantom digits on screen), and the same tone energy
  disturbed the tail/squelch detector, so the audio opened and closed.
- **Cause:** `RADIO_SetupRegisters()` enabled the DTMF decoder and set its interrupt
  mask bit **unconditionally** on every RX reconfigure. Turning `D Live` off called
  `BK4819_DisableDTMF()`, but the same menu handler then requested a VFO
  reconfigure, which re-enabled it within milliseconds.
- **Fix:** the receiver now honours `D Live` and leaves the DTMF interrupt out of the
  mask when the decoder is off, so a false digit cannot be latched at all.
  **DTMF transmit is unaffected** — PTT-ID and DTMF-ID still key exactly as before.

### 2. RX could stay silent or the S-meter read wrong after the spectrum view (RX-11)

- **Problem:** after using the spectrum analyser, the radio could be left with the
  AGC disabled or a stale gain table, so audio stayed silent or the S-meter was
  wrong — until some unrelated action happened to change the modulation.
- **Cause:** `RADIO_SetupAGC()` skipped its register writes whenever its arguments
  matched the previous call, via a private static cache. That assumption was wrong:
  the spectrum code writes the AGC gain table directly, and the cache key never
  changed on the spectrum path at all. `RestoreRegisters()` restores the AGC enable
  bit but not the gain table, so the bad state survived leaving the spectrum.
- **Fix:** the unsound cache is gone — the AGC is now programmed from the requested
  state every time. The spectrum's listen mode freezes the AGC while tuning to a
  peak and restores it afterwards, and the register-menu AGC lock does what it says.

### 3. RX audio could be armed with the amplifier only, leaving one VFO silent (RX-12)

- **Problem:** on one VFO — typically VFO B, with dual watch on, and often after
  visiting the spectrum view, transmitting, or playing a tone — the S-meter moves
  and the squelch opens but **nothing comes out of the speaker**. The receiver was
  working; the audio path behind it was not.
- **Cause:** `AUDIO_AudioPathOn()` is a one-line helper that drives *only* the
  amplifier enable GPIO. It never re-asserts the BK4819's own audio enables,
  `REG_30<9>` (AF DAC) and `REG_47<8>` (AF output), and neither did the RX entry
  (`APP_StartListening()` called the GPIO helper and nothing else). Both bits are
  global rather than per VFO, and several code paths legitimately leave them
  cleared — the spectrum sweep, for instance, caches `REG_30` with the AF DAC
  masked off and rewrites that value on every step. If RX then started with the
  GPIO alone, the chip kept demodulating into a disabled DAC.
- **Fix:** the receiver now re-asserts both chip bits on **every** RX entry, and
  the ordering is pop-controlled: chip enables first, 500 µs settle, amplifier
  un-muted last (on exit, the reverse). This is adopted verbatim from the
  **UV-K1Series ApeX Edition** firmware, which replaced the scattered GPIO
  toggles with exactly this centralized `RADIO_SetAudioPath()`.
- **Also new:** `tools/rx_probe_vfo.ps1` decodes the per-VFO EEPROM records, so the
  *other* cause of a VFO-B-only silence — a stale `RxCTCS`/`RxDCS` code or a
  non-FM mode stored in that VFO's 16-byte record — can be identified with
  `k5prog -R -E -f eeprom.bin` instead of guessed at. It can also write a
  corrected image (`-PatchTo`), never the original. Procedure:
  [`Documentation/VFO_RX_SILENCE_DIAGNOSTIC.md`](Documentation/VFO_RX_SILENCE_DIAGNOSTIC.md).

### 4. Local build helper repaired (tooling, not firmware)

`tools/build_k5.ps1` had drifted out of sync with the Makefile and had not produced
a valid link since the spectrum work landed — it referenced a file that does not
exist, omitted three sources, and omitted the spectrum define entirely, so the size
it printed was meaningless. It now derives the version and every feature toggle from
the Makefile at run time.

> **Note:** a local (non-Docker) toolchain produces an image ~620 B **larger** for
> identical code, which can exceed the flash budget for a configuration that is
> perfectly fine in the release build. Always take release figures from
> `./compile-with-docker.sh ApeX`.

## Verification

- Build: `-Oz -Wall -Wextra -Werror`, LTO + `--gc-sections` — **0 warnings / 0 errors**.
- Byte-exact release measurements, each taken on the same image for a like-for-like
  comparison:

  | Build | FLASH | RAM | free |
  |---|---|---|---|
  | v7.6.10B | 61,364 B | 3,564 B | 76 B |
  | v7.6.10C (items 1-2) | 61,348 B | 3,560 B | 92 B |
  | v7.6.10C (items 1-3) — **shipped** | **61,396 B** | **3,560 B** | **44 B** |

  Items 1-2 *reduce* size (net **−16 B FLASH, −4 B RAM** against v7.6.10B). Item 3
  adds **+48 B FLASH, 0 B RAM** — predicted as a delta on the same tree
  (61,956 B → 62,004 B, local `arm-none-eabi-gcc 14.3.Rel1`) and confirmed by the
  byte-exact release build (61,348 B → 61,396 B). The image stays inside the
  61,440 B flashable window with **44 B free**, so no feature had to be cut.
- Diagnostic tool: `tools/rx_probe_vfo.ps1` was validated against a synthetic 8 KiB
  EEPROM image covering all decode paths (erased records, CTCSS, DCS, reverse mode,
  airband, out-of-range nibbles, A/B byte diff) and against its three guard rails
  (non-existent file, Intel HEX input, truncated image), including a patch
  round-trip that clears the reported `CRIT` rows.
- **Bench pass recommended.** These fixes are code-verified and build-verified but
  not yet confirmed on hardware. On the channel/VFO that showed the fault, please check:
  1. spurious DTMF digits stop appearing — or keep appearing if that repeater really
     does carry DTMF, in which case the digits are real and the UHF squelch table is
     the next thing to look at;
  2. entering and leaving the spectrum view leaves audio and the S-meter correct;
  3. PTT-ID / DTMF-ID still key correctly;
  4. the silent VFO now produces audio — directly after leaving the spectrum view,
     after a transmission, and after a beep/tone, with dual watch toggling between
     both VFOs;
  5. no new pops or clicks are audible when RX starts or stops.
